# Frondend Rule

前端开发必须以工程一致性、可维护性、可访问性、性能和真实用户体验为优先级。实现功能前先理解当前项目已有技术栈、目录结构、组件模式和设计语言，再决定是否新增抽象或依赖。

## 工程约束

- 使用 monorepo 组织项目，优先通过 workspace 复用包、类型、工具配置和 UI 基础能力。
- 包管理统一使用 `pnpm`，依赖版本统一放在 pnpm catalog 中维护。
- 不混用 `npm` 或 `yarn`。
- 新增依赖前先确认项目中没有已有等价能力；确需新增时说明用途、替代方案和体积影响。
- 代码风格遵循项目 ESLint、TypeScript、格式化和命名约定，不引入另一套风格。
- 不做无关重构，不顺手改动不属于当前任务的文件。

## 技术选型

- 样式优先使用 Tailwind CSS，并复用已有 design tokens、颜色、间距、圆角、阴影和断点。
- 组件库优先使用项目已有方案；需要无样式原语时优先 Radix UI。
- React 项目可使用 ahooks；引入前确认它确实减少复杂度而不是隐藏业务逻辑。
- Vue 项目优先使用 Vue 3 Composition API、`<script setup lang="ts">`、明确的 props/emits 数据流。
- 图标优先使用项目已有图标库，例如 Iconify 或 lucide，不手写重复 SVG。
- 重型编辑器、图表、地图、富文本、3D 或 AI 组件必须按需加载。

## UI 与交互

- 直接构建可用界面，不做空洞的展示页。
- 信息架构优先清晰、密度合理、可扫描；后台和工具类界面避免营销式大 hero。
- 弹窗、抽屉、编辑器和表单必须给足可编辑空间，长内容不能挤在小容器里。
- 所有交互元素都要有明确的 hover、focus、active、disabled、loading 和错误状态。
- 图标按钮必须提供可理解的 `aria-label` 或可见文本。
- 文本不能溢出、遮挡或和其他元素重叠；长文本使用截断、换行或布局约束处理。
- 不用颜色作为唯一信息表达方式，状态变化要有文字、图标或结构辅助。
- 表单提交、删除、覆盖、远程同步等操作必须有明确反馈，危险操作必须可确认或可撤销。

## 响应式布局

- 默认同时考虑移动端、平板和桌面，不只为当前屏幕写死尺寸。
- 固定格式元素要使用稳定尺寸、`min/max`、`aspect-ratio` 或明确网格，避免 hover、加载和内容变化导致布局跳动。
- 工具栏、按钮组、标签、卡片列表在窄屏必须能换行或折叠，不得横向溢出。
- 触控目标尺寸要足够，移动端不要依赖 hover 才能发现功能。

## 组件与状态

- 组件职责保持单一，复杂页面拆分为容器组件、展示组件和必要的 composable/hooks。
- 父组件负责业务编排，子组件通过 props/emits、回调或明确的状态接口通信。
- 避免在模板或 JSX 中写复杂表达式，复杂派生数据放到 computed、memo 或独立函数中。
- 表单状态、请求状态、筛选状态和弹窗状态要有单一可信来源。
- 异步请求必须处理 loading、empty、error、success 四类基本状态。
- 用户输入、文件路径、URL、远程数据和 Markdown/HTML 内容必须做安全校验。

## 数据与 API

- API 调用要有清晰的请求体、响应体和错误处理，不依赖隐式字段。
- 前端不要吞掉后端错误；需要把可行动的错误信息展示给用户。
- 对列表、搜索、分页、排序、筛选等状态，优先使用可复现的数据结构。
- 修改文件、删除资源、同步远程、覆盖内容等操作要避免路径穿越和越权写入。
- 乐观更新必须能回滚；无法回滚时等服务端成功后再更新 UI。

## 可访问性

- 使用语义化 HTML 和合理标题层级。
- 输入框必须有关联 label 或 `aria-label`。
- 键盘焦点必须可见，核心流程应能用键盘完成。
- 弹窗打开后应聚焦到主要操作或第一个可编辑字段，关闭后返回触发元素。
- 使用图片、图标或状态色时，要提供文本替代或辅助说明。

## 性能

- 大依赖按需加载，必要时拆分 chunk。
- 列表、搜索和过滤避免在模板中重复执行高成本计算。
- 大列表考虑分页、虚拟滚动或服务端查询。
- 图片和媒体资源必须有尺寸约束，避免布局抖动。
- 频繁输入、滚动、resize 等事件要节流、防抖或使用浏览器原生能力。
- 构建产物明显增大时，需要说明原因并优先优化加载路径。

## 测试要求

- 修改共享逻辑时补充单元测试。
- 修改用户流程、表单、弹窗、编辑器、路由或权限时补充集成测试或端到端验证。
- 使用 Vitest 作为默认单元测试框架，优先覆盖关键业务逻辑、公共组件和边界条件。
- UI 行为修改后必须通过浏览器实际验证关键路径。
- 测试要验证真实行为，不只验证实现细节或 mock 调用次数。
- 无法自动化验证时，在交付说明中写清楚手动验证步骤和结果。

## 交付检查

- 运行项目既有的 lint、typecheck、test、build 命令。
- 检查控制台是否有 error 或明显 warning。
- 检查新增 UI 在移动端和桌面端都不会溢出或遮挡。
- 检查空状态、错误状态、加载状态和禁用状态。
- 检查是否引入敏感信息、硬编码路径、临时调试日志或无关文件改动。
